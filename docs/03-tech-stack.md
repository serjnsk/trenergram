# Технологический стек

Принятый стек продукта: **один веб-стек на все три интерфейса** — React + Vite + Ionic в вебе, он же через Capacitor собирается под iOS и Android. Отклонения и запасной путь — в разделе «Альтернативы».

## Состав стека

### Клиентская часть

Ядро — **один веб-стек на все три интерфейса**: то же приложение собирается в браузер и, через Capacitor, в нативные iOS- и Android-пакеты.

| Слой | Технология | Обоснование |
|---|---|---|
| Приложение (веб + iOS + Android) | **React + Vite + Ionic**, TypeScript | Одна кодовая база покрывает кабинет тренера, мобильного тренера и клиента; вёрстка переносится из макетов один в один — обычный DOM и CSS, без пересборки под нативный рендер |
| Сборка под мобильные | **Capacitor** | Нативные пакеты из того же исходника; доступ к системным возможностям — плагинами, свои пишутся на Swift и Kotlin |
| Публичная страница тренера (BRD-2, этап 3) | Отдельный небольшой Next.js-сайт | Нужен SEO; не тащить SSR в основное SPA ради одной фичи |
| Монорепо | **pnpm workspaces + Turborepo** | Общие пакеты: `domain-types`, `workout-parser`, `api-client`, `design-tokens` |

### Оффлайн и синхронизация — ключевое решение

**[PowerSync](https://powersync.com/) (self-hosted) + SQLite на клиенте + PostgreSQL на сервере.**

- На устройстве — полноценная SQLite: на iOS и Android нативная через `@capacitor-community/sqlite`, в браузере wa-sqlite. SDK сам выбирает движок по среде, код работы с данными один. Приложение всегда читает и пишет локально — мгновенный UI и честный оффлайн (CLI-3, CLI-4).
- PowerSync Service реплицирует нужные данные из Postgres в клиентскую SQLite по декларативным sync-правилам (bucket'ы: клиент видит свои программы, тренер — своих клиентов).
- **Записи идут через upload queue в наш backend API** — критично для бизнес-правил: сервер, а не клиент, решает вопросы доступа (блокировка при неоплате PAY-1/PAY-5), валидации и прав. Ретраи и очередь оффлайн-записей SDK берёт на себя (CLI-5).
- Self-hosted редакция закрывает требование 152-ФЗ — весь контур в РФ.
- Медиа (GIF, видео) через PowerSync **не** синхронизируется — только структурированные данные; загрузкой медиа управляет отдельный кэш-слой по правилам из раздела «Оффлайн» ниже.

Почему PowerSync, а не альтернативы:

| Вариант | Вердикт |
|---|---|
| **PowerSync** | ✅ Единственный зрелый sync-движок с отдельным SDK под Capacitor; self-hosted; Postgres |
| ElectricSQL | Хорош для веба, но это read-path-движок общего назначения |
| WatermelonDB | Только локальная БД, серверный sync-протокол пишем сами — лишний объём работы |
| CRDT (Automerge/Yjs) | Для совместного редактирования документов; наша модель данных реляционная, конфликтов мало — overkill |
| Самописный sync | Классическая яма на месяцы; берём готовое |

### Серверная часть

| Слой | Технология | Обоснование |
|---|---|---|
| API | **Node.js + TypeScript, NestJS** (или Fastify) | Один язык с клиентами; структура NestJS удобна при росте команды |
| Контракт API | tRPC внутри монорепо (или REST + OpenAPI — по вкусу команды, некритично) | End-to-end типы против целого класса багов |
| БД | **PostgreSQL 16+** | Источник истины; требование PowerSync |
| Очереди | Redis + BullMQ | Уведомления (NTF-1), еженедельные анкеты (SUR-1), транскодинг видео |
| Файлы и видео | S3-совместимое хранилище РФ (Яндекс Object Storage / Selectel) + ffmpeg-воркеры + HLS | VID-1 (этап 2); стоимость хранения закладывается в тарифы |
| Auth | Телефонный OTP: СМС-провайдер РФ (SMS Aero / SMSC), дешёвые альтернативы — flash call, Telegram Gateway; JWT + refresh | REG-2; Firebase Auth в РФ не опора |
| Push | FCM + APNs через Capacitor Push Notifications | NTF |
| Платежи (этап 2) | **Т-Банк** (интернет-эквайринг / касса) | Уже используется в других продуктах основателя |
| Хостинг | Яндекс Cloud / Selectel (managed Postgres + Docker Compose на старте) | 152-ФЗ; Kubernetes на старте не нужен |
| Мониторинг | Sentry (crash + errors), простые метрики | Скорость конструктора — продуктовая метрика (NFR-4), меряем с первого дня |

### Библиотеки под ключевые фичи

Библиотека одна на все платформы — мобильные собираются из того же кода:

| Фича | Чем делаем |
|---|---|
| Drag-and-drop (CON-8) | dnd-kit — один и тот же код в вебе и в мобильной сборке |
| Графики (PRO-6) | recharts |
| Таймер (TMR-1…4) | Capacitor-плагины: фоновое аудио, локальные уведомления, keep-awake; на Android — foreground service |
| HealthKit и носимые (INT-1, этап 3) | Capacitor-плагин; при нехватке готового — свой на Swift/Kotlin |
| Парсер «EMOM 12» (TMR-1, CON-5) | Общий TS-пакет `workout-parser`, правила и грамматика, без LLM в MVP |

## Оффлайн: что синхронизируется и сколько весит

Детализация CLI-3…CLI-5 и NFR-3: что именно лежит на устройстве, что догружается по правилам, а что работает только онлайн.

### Три уровня данных

##### Уровень 1 — всегда на устройстве (полная синхронизация)

Структурированные данные — лёгкие, синхронизируются целиком через PowerSync:

| Данные | Оценка объёма |
|---|---|
| Метаданные всей базы упражнений (~1 500 шт.: названия RU/EN, инструкции, мышцы, оборудование, связи замен/прогрессий) | ~5–10 МБ |
| Программы, тренировки, результаты пользователя (клиент — свои; тренер — своих клиентов) | < 5 МБ за год активного использования |
| Профили, ПМ, история показателей, комментарии, шаблоны тренера | < 5 МБ |
| **Итого уровень 1** | **~10–20 МБ** — незаметно для пользователя |

Вывод: **вся текстовая часть продукта оффлайн всегда**, для любого объёма клиентов тренера. Ограничивать нужно только медиа.

##### Уровень 2 — prefetch по правилам (упреждающая загрузка медиа)

Медиа, которое понадобится с высокой вероятностью, качается заранее, пока есть сеть:

- **GIF упражнений из назначенных тренировок** на ближайшие 7–14 дней (клиент) — тренировки известны заранее, это и есть главный оффлайн-сценарий.
- **Видео тренера, привязанные к назначенным тренировкам** (этап 2) — по настройке «загружать только по Wi-Fi».

| Сценарий | Оценка |
|---|---|
| Неделя тренировок клиента: ~5 тренировок × ~10 упражнений = ~50 GIF × 0,3–1 МБ (360×360) | **~15–50 МБ** |
| Видео тренера к неделе тренировок (если есть): 2–3 ролика × 30–100 МБ | ~60–300 МБ — только по Wi-Fi, по настройке |

##### Уровень 3 — только онлайн (+ кэш после просмотра)

- Свободный браузинг всей медиабазы упражнений (GIF грузятся на лету, просмотренные остаются в LRU-кэше).
- Стриминг видео тренера вне prefetch-окна.
- Лидерборды, публичные страницы, платежи, загрузка новых видео.

### Почему не «вся база оффлайн»

| Вариант | Объём | Вердикт |
|---|---|---|
| Вся база GIF 360×360 (~1 400 шт.) | ~0,5–1,5 ГБ | ❌ Недопустимо как дефолт |
| Вся база GIF 180×180 | ~300–500 МБ | ⚠️ Как дефолт — нет; допустимо как **опция** для тренера: «Скачать базу целиком» (по Wi-Fi), для работы в залах без связи |
| Метаданные + prefetch назначенного | ~30–70 МБ | ✅ Дефолт |

### Правила кэша

- Лимит медиакэша по умолчанию: **500 МБ**, вытеснение LRU; размер настраивается в приложении.
- Prefetch — только по Wi-Fi по умолчанию (настройка: «и по мобильной сети»).
- Очередь исходящих: результаты/комментарии (лёгкие — уходят сразу при появлении сети), видео клиента (тяжёлые — по Wi-Fi, с индикатором «ожидает отправки»).

### Следствия для реализации

1. **Sync-правила PowerSync (bucket'ы):** уровень 1 описывается декларативно — «клиент видит свои назначения», «тренер видит своих клиентов». Медиа в PowerSync не синхронизируется вообще — только URL; загрузкой управляет отдельный media-cache-слой приложения.
2. **Оценки объёмов проверяются на сэмпле EDB** (30 бесплатных GIF — реальные размеры файлов) в рамках спайка №1 из разделе «Обязательные спайки» ниже.
3. Дизайнеру: состояния «GIF ещё не загружен» (плейсхолдер со схемой/названием), «видео ожидает Wi-Fi», «результат ожидает синхронизации» — обязательные состояния UI, а не крайние случаи.

## Стартовая база упражнений

Контент базы (EX-1) покупается разовым выкупом датасета с хостингом у себя: живой внешний API несовместим с оффлайн-архитектурой — упражнения должны лежать в нашем Postgres и синхронизироваться на устройства (NFR-3).

Выбран **EDB Exercise Intelligence** ([exercisedb.io](https://exercisedb.io/pricing)), лицензия Cross-Platform — $599 разово: 1 394 упражнения, GIF в четырёх разрешениях, 17 полей метаданных, связи «похожие / замены / прогрессии / регрессии». Импорт в наш Postgres, GIF — в S3-хранилище.

Своими силами добавляются две вещи: русская локализация названий и инструкций (AI-1 и вычитка) — русского нет ни у одного поставщика; и ~80–120 кроссфит-движений (ТА-вариации, гимнастика, double-unders, wall ball, эргометры), которые generic-базы покрывают лишь частично.

## Почему не React Native, не Flutter и не нативная разработка

- **React Native.** Отклонён по опыту команды. Часть плагинов приходит сырыми и всё равно требует доработки; обновление плагина может некорректно накатиться или затереться при синхронизации; обновления привязаны к версии RN, и после них уходит много времени на сопоставление библиотек — приложение подолгу не запускается из-за ошибок, а ставить эти обновления почти всегда приходится. Отдельная сложность — точно повторить макет: стили и SVG рендерятся иначе. В плюс RN идут готовая обвязка к системным возможностям (HealthKit, виджеты) и поведение инпутов и сплэш-экранов «из-под капота», но это не перевешивает.
- **Flutter:** веб-конструктор — ядро продукта, а Flutter Web (canvas-рендеринг) слаб для текстонагруженных рабочих SPA: инпуты, буфер обмена, доступность, вес бандла. Пришлось бы писать веб отдельно на React → два стека и два набора компетенций.
- **Нативная разработка / Kotlin Multiplatform:** три UI-кодовые базы (SwiftUI, Compose, веб) — не по бюджету маленькой команды на скорости, которая нам нужна.

### Что учесть на старте

Capacitor снимает риски React Native, но приносит два своих — оба закрываются спайком №1:

1. **SDK PowerSync под Capacitor — в статусе beta.** Основная часть унаследована от стабильного Web SDK, а нативный драйвер `@capacitor-community/sqlite` разработчики называют production-ready для проверенных сценариев. Но оффлайн — главный технический риск проекта, и опираться на beta нужно осознанно, проверив свои сценарии первыми.
2. **Шифрование локальной базы на iOS и Android в этом SDK недоступно.** На устройстве лежат персональные и медицинские данные (PRO-3, 152-ФЗ) — нужно решить, чем закрывать: шифрованием на уровне приложения, ограничением состава локальных данных или ожиданием поддержки в SDK.

## Обязательные спайки перед стартом (первая неделя разработки)

1. **PowerSync end-to-end на Capacitor:** сборка под iOS и Android плюс веб, sync-правила «тренер видит своих клиентов», оффлайн-запись результата → синхронизация. Главный технический риск проекта; здесь же проверяются оба ограничения beta-SDK.
2. **Drag-and-drop длинной тренировки** в мобильной сборке: 60fps на списке из 30+ упражнений в WebView — узкое место именно веб-стека на телефоне, проверять на реальном устройстве, а не в симуляторе.
3. **Парсер тренировочной нотации:** «EMOM 12», «10 rounds / 30 sec work / 15 sec rest», заголовки суперсетов («Суперсет 3 круга») — прототип грамматики. Отдельно проверить кириллицу: `\w` в регулярных выражениях русские буквы не матчит, правила пишутся явными диапазонами.

Спайк таймера (звук и вибрация при заблокированном экране — TMR-2, TMR-3) проводится перед началом этапа 2.

## Альтернативы

Если спайк №1 покажет, что beta-SDK не держит наши сценарии, запасной путь — оставить мобильные на том же Capacitor, но временно сузить оффлайн до чтения программы с очередью исходящих записей поверх обычного API, а полноценный двусторонний sync подключить, когда SDK дойдёт до стабильного релиза. Серверная часть при этом не меняется.
